Dependency upgrade and code migration plan

Prepared on July 11, 2026.

Current outcome

All compatible direct dependencies were upgraded to their newest published releases. npm audit reports zero vulnerabilities, and the project builds and type-checks successfully.

The ESLint 10, plugin, glob, Node type, and Vitest upgrades required no application-code changes. ESLint 10 requires Node 20.19 or newer, so the package engine declaration was raised to >=20.19.0.

TypeScript 5.9.3 7.0.2 typescript-eslint@8.63.0 declares TypeScript support only for >=4.8.4 <6.1.0. Installing TypeScript 7 now would create an unsupported peer dependency combination.

Do not force TypeScript 7 into the current dependency graph. Begin the migration after a typescript-eslint release officially supports TypeScript 7.

TypeScript 7 migration steps

  1. Confirm the compatibility gate: verify the latest typescript-eslint and @typescript-eslint/parser peer ranges include TypeScript 7, and verify their Node engine requirement.
  2. Create a focused upgrade branch: update TypeScript, typescript-eslint, and its parser together; regenerate package-lock.json with the supported Node version.
  3. Review compiler configuration: run tsc --showConfig, compare TypeScript 7 defaults and removed/deprecated options with tsconfig.json, then make explicit configuration changes where behavior would otherwise drift.
  4. Resolve source diagnostics: run npm run typecheck and update code for changed standard-library types, module resolution, declaration emit, or stricter inference. Keep fixes narrowly scoped and add regression tests for behavior-affecting changes.
  5. Validate scanner integration: restore or recreate the currently absent test/fixtures directory, then run the complete integration suite so ESLint parser behavior is exercised against representative JavaScript and TypeScript inputs.
  6. Verify release artifacts: run build, unit tests, integration tests, npm audit, npm ls --all, and npm pack --dry-run under every supported Node major in CI.
  7. Release safely: document the new minimum Node version if it changes, publish as a major version if consumer-facing types or runtime behavior change, and retain the prior lockfile/tag as the rollback point.

Acceptance criteria

  • No npm vulnerabilities and no invalid required peer dependencies.
  • Type-check, build, unit tests, integration tests, and package dry-run all pass on supported Node versions.
  • Scanner output for the fixture corpus is unchanged unless an intentional change is documented.
  • No forced or legacy peer-dependency resolution flags are needed for a clean install.
