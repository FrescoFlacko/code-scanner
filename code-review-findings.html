High severity

1. Fatal scanner errors are absent from totals and can be omitted from priorities

High — src/scanner/report/buildReport.ts:39-55,102; src/scanner/report/calculateTotals.ts:3-27; src/scanner/report/calculatePriorities.ts:5-12,15-30,57-66

Evidence: a parser failure now correctly forces grade F and creates an other/scanner-error issue, but totals have no scanner-error count and priority score ignores it. Reproduction with one malformed and one valid TypeScript file reported the broken file as F with score 0 and reason “Most Issues (0 total),” below the valid A-grade file. With three positive-score files, the malformed file drops out of the top-three priorities entirely.

Impact: the most fundamental scan failure can be absent from the summary and recommended remediation order.

Fix: add a first-class scanner-error metric to file reports, totals, history, JSON, and priority impact. Give scanner errors priority above rule findings and use a clear primary reason such as “File could not be analyzed.”

Medium severity

2. Blanket-enabling all Sonar rules creates policy-dependent false positives

Medium — scanner.config.ts:107-129

Evidence: every exported Sonar rule is enabled with "warn", including rules that represent optional organizational policy or need configuration. A minimal valid file containing only export const x = 1 is reported for sonarjs/file-header even though the scanner has no configured header format. The self-scan currently emits 605 maintainability findings across 39 files.

Impact: noisy or meaningless findings reduce trust in grades and can bury actionable defects.

Fix: maintain a curated default profile of context-free rules. Put policy/framework/type-aware rules behind explicit configuration, validate required options, and add golden fixture tests for the default profile.

3. Overall improvement percentage uses a different model from priority scoring

Medium — src/scanner/report/calculatePriorities.ts:5-12,83-98

Evidence: priority scores include cognitive and cyclomatic complexity, but totalWeightedIssues and top3WeightedIssues exclude both. A scan whose priorities are driven only by complexity reports an overall improvement estimate of 0% even though projected grades assume those metrics are fixed.

Fix: define one canonical impact-weight function and reuse it for sorting and the numerator/denominator, or rename the percentage to state that it covers issue counts only.

4. Zero-score clean files are still presented as priorities

Medium — src/scanner/report/calculatePriorities.ts:57-71

Evidence: the function sorts every report entry and always slices three. Repositories with fewer than three files needing work receive arbitrary score-zero entries with “Most Issues (0 total).”

Fix: filter to actionable entries before taking the top three. Scanner errors must remain actionable through finding 1’s dedicated metric.

5. History validation accepts impossible metric ranges

Medium — src/scanner/history/loadHistory.ts:32-44

Evidence: validation checks only that metrics are finite. A version-1 history containing negative issue counts and complexity plus commentRatio: 500 was accepted and returned as valid.

Impact: corrupted or manually edited state can produce nonsensical trend deltas while appearing schema-valid.

Fix: require non-negative integer counts, non-negative complexity values, and a comment ratio within 0–100. Cross-check totals.files against the file map when history represents a full scan.

Low severity and performance improvements

6. JSON metadata still omits built-in effective exclusions

Low — src/scanner/index.ts:97-100; src/scanner/files/resolveFilesToScan.ts:8-13,26

The JSON artifact records merged CLI/config excludes but not the default dependency/build/VCS exclusions actually used. Reports therefore remain not fully reproducible. Return effective discovery options from one owner or include separate defaultExcludes, configuredExcludes, and final effectiveExcludes fields.

7. JSON output writes are not atomic

Low — src/scanner/output/writeJsonOutput.ts:13-16

An interrupted process or concurrent readers can observe a truncated report. Use a unique same-directory temporary file with exclusive creation, then rename atomically, matching the hardened history writer.

8. The async public API still performs blocking per-file and Git operations

Low — src/scanner/git/getGitChangedFiles.ts:7-20; src/scanner/metrics/calculateCommentRatio.ts:23-24

execFileSync, realpathSync, and one synchronous source read per result block embedding applications on large repositories. Convert Git execution and file reads to async APIs, or reuse source text from the lint pipeline where available.

  3. Unify priority scoring and improvement calculations; remove zero-score priorities.

  5. Harden JSON writes and finish async I/O conversion.
