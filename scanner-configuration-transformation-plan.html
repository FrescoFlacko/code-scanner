Scanner configuration transformation plan

Prepared July 11, 2026.

Goal: replace the current “enable every rule” configuration with a low-noise portable core, explicit Lambda and Angular profiles, a metrics-only layer, and versioned rule metadata that fails visibly when SonarJS changes.

Target outcome

Architecture

Key decision: profiles are explicit configuration contracts. Detection may recommend a profile, but must not silently change enabled rules. A scan artifact must record the selected profiles, versions, effective rules, options, and ignores.

1. Separate four concepts

  1. Rule inventory: what rules installed plugins expose.
  2. Rule classification: security, correctness, maintainability, cleanliness, policy, framework, or metric.
  3. Profiles: which classified rules apply in a given runtime/framework.
  4. Scoring: how findings and measurements affect grades, priorities, and CI.

Today these concepts are collapsed into scanner.config.ts. Each should have one owner and tests.

2. Proposed source layout

src/scanner/config/
  schema.ts                    # runtime-validated public config contract
  resolveConfig.ts             # deterministic profile + override composition
  ruleInventory.ts             # installed plugin inventory
  manifests/
    sonarjs-4.json              # reviewed classification and compatibility data
  profiles/
    recommended.ts             # generic low-noise JS/TS baseline
    metrics.ts                 # measurement rules, excluded from issue totals
    strict.ts                  # opt-in maintainability expansion
    security.ts                # high-confidence portable security
    node.ts                    # Node runtime globals/module semantics
    lambda.ts                  # Lambda/serverless additions
    angular.ts                 # Angular TS rules
    angular-template.ts        # Angular HTML processor/parser/rules
  scoring.ts                   # one canonical score/priority model

3. Public configuration contract

{
  "profiles": ["recommended", "node", "lambda"],
  "mode": "advisory",
  "typescript": { "typeAware": "auto" },
  "rules": {
    "sonarjs/no-duplicate-string": ["warn", { "threshold": 5 }],
    "sonarjs/file-header": "off"
  },
  "metrics": {
    "cognitiveComplexity": true,
    "cyclomaticComplexity": true
  },
  "exclude": ["**/*.generated.ts"]
}

Validate this file at the disk boundary. Reject unknown profile names, unknown rule IDs, incompatible rule options, and contradictory settings. The resolved configuration should be immutable and included in JSON output.

Generic recommended profile

  • Start from plugin-maintained recommended configurations where stable, then pin explicit deltas.
  • Exclude policy rules such as file headers, naming conventions, formatting, framework assumptions, and cloud-provider rules.
  • Use practical violation thresholds, for example cognitive complexity around 15 and cyclomatic complexity around 10–15, validated against representative repositories.
  • Do not treat low comment ratio as a universal defect; report it as information unless a project opts into documentation policy.
  • Classify unreviewed new rules as unclassified and keep them disabled.

Lambda profile

  • Compose the generic, security, and Node profiles rather than duplicating their rules.
  • Support both ESM and CommonJS based on explicit config/package metadata.
  • Apply Lambda-specific guidance: thin handlers, initialization outside the handler where appropriate, controlled dependencies, async completion, and typed event/context contracts.
  • Enable only relevant AWS rules; infrastructure-as-code rules should apply to CDK/CloudFormation source patterns, not ordinary handler files.
  • Add purpose-built checks only when they are reliably AST-detectable: unawaited async work, callback/promise mixing, secrets in environment fallbacks, unsafe event trust, non-idempotent batch processing hotspots, and clients repeatedly created inside handlers.
  • Keep architectural recommendations advisory unless the project declares conventions such as handler paths.

Angular profile

  • Use the angular-eslint package matching the Angular major version.
  • Lint .ts with TypeScript/Angular rules and .html with @angular-eslint/template-parser.
  • Support inline templates through the official processor.
  • Scope component/directive selector and naming policies to explicit project configuration; do not invent defaults for existing repositories.
  • Separate app, library, spec, generated API client, and template overrides using flat-config files/ignores.
  • Prefer Angular’s recommended configurations as a version-aligned base, with scanner-specific categorization layered on top.

SonarJS upgrade portability

  1. Generate inventory: extract every installed rule ID, metadata, docs URL, schema, defaults, deprecation state, and plugin version.
  2. Compare with reviewed manifest: CI fails when a rule is added, removed, renamed, deprecated, or changes schema/default options.
  3. Default-deny new rules: new rules remain disabled and unclassified until reviewed.
  4. Record rationale: every enabled rule has profile membership, category, confidence, default severity, option values, and a short reason.
  5. Test real fixtures: each enabled rule needs at least one positive or curated representative fixture; profiles need clean-repository golden tests.
  6. Version manifests by plugin major: avoid one growing compatibility map with conditionals.
  7. Automate upgrade PR evidence: attach inventory diff, fixture changes, finding-count delta, runtime change, and false-positive review.

Do not infer security classification from English rule descriptions. Prefer reviewed manifest data tied to rule IDs and upstream documentation; fail visibly when the inventory drifts.

Scoring and restriction changes

  • Introduce finding confidence: error, warning, hotspot, policy, and metric.
  • Metrics do not count as issues. A separate threshold evaluator converts a measurement into a finding only when it exceeds the selected profile threshold.
  • Security hotspots require review and should not automatically be labeled confirmed vulnerabilities.
  • Grades should use normalized rates or bounded per-file effects so large files are not punished solely for size.
  • CI gates initially cover scanner errors and high-confidence correctness/security only. Maintainability stays advisory until calibrated.
  • Offer advisory, recommended, and strict modes with documented semantics, not hidden threshold multipliers.

Testing strategy

  • Manifest contract tests: installed inventory exactly matches the reviewed versioned manifest.
  • Profile snapshot tests: resolved rule IDs/options for each profile are intentional and reviewable.
  • Golden integration repositories: generic Node library, Lambda API/SQS handlers, Angular app/library/templates, mixed monorepo.
  • Noise tests: clean idiomatic fixtures have bounded finding counts and no policy rules unless opted in.
  • Positive tests: known security/correctness defects are detected and correctly categorized.
  • Upgrade tests: run old and new plugin versions against the corpus and publish finding deltas.
  • Performance tests: type-aware and template profiles have explicit time/memory budgets.

Success measures

  • At least 80% reduction in findings on clean representative repositories.
  • No unreviewed rule becomes enabled after a dependency upgrade.
  • Zero security rules silently reclassified by metadata wording changes.
  • Generic profile works without Angular/AWS dependencies installed.
  • Angular templates and Lambda handlers receive profile-specific coverage.
  • Scanner JSON fully records profile names, manifest/plugin versions, effective rules, options, ignores, and scoring version.
  • Only high-confidence scanner/correctness/security failures gate CI by default.
